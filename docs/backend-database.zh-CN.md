# 采集 Demo 的后端与数据库方案

状态：2026-11-16 设计草案；尚未接入 Unity、尚未部署数据库。

## 现在的建议

先把当前采集做成可靠的本地单人版本；联网第一阶段按“小规模独立世界、可持续保存”设计。建议后端使用 ASP.NET Core，持久化使用 PostgreSQL。Unity 不直连数据库。实时世界先由一个权威进程独占运行；若沿用现有 NavMesh，可先用 Unity Dedicated Server/无界面运行来复用行为逻辑，ASP.NET Core 处理身份、进入世界、存档与管理 API。两者的持久化请求只经过后端内部接口。

目前没有现有后端或数据库可迁移。本文默认未来有联网需求，不假定会做 MMORPG、全球共享市场或千人同屏；如果最终仅做离线单人，本地版本化存档即可，数据库可以暂时不部署。离线客户端上传的存档只能进入非竞争的个人世界，不能直接进入有可信经济的联机世界。

第一阶段先保持单体服务和一个 PostgreSQL 实例。Redis、消息队列、分库分表在出现跨进程协调或实测瓶颈后再引入。现在不需要为每个工人的每一帧位置建数据库写请求。

## 谁负责什么

| 层 | 职责 | 不承担的职责 |
| --- | --- | --- |
| Unity 客户端 | 选人、目标提示、发送命令、画面插值、显示服务器状态 | 自行决定联网资源产量或库存增减 |
| 世界权威进程 | 移动、寻路、占位、采集、重量与速度、任务队列；验证所属权和目标；生成结果 | 将位置逐帧写入数据库 |
| 后端 API | 身份、世界权限、分配世界进程、版本校验、幂等提交、存档事务 | 通过普通 HTTP 每帧驱动寻路 |
| PostgreSQL | 世界检查点、已处理命令、资源转移记录、规则版本、成员权限 | 运行游戏循环和承担实时广播 |
| 统计文件/后续分析存储 | 吞吐量、排队耗时、性能与调参对照 | 作为玩家库存的权威数据 |

客户端发“让这几名工人采集这棵树”，不能发“给库存增加 6 木材”。多人一起操作同一队工人时，第一版只允许拥有控制权的成员下令；共享控制可以以后明确规则再开放。

## 数据库第一版：保存一致的世界，而不是先拆几十张表

小世界第一版采用一个版本化 JSONB 世界状态，加必要的关系表。一次存档必须同时包含：

- 世界 ID、存档格式版本、规则版本、tick、随机种子/随机状态。
- 资源节点稳定 ID、资源种类、位置、剩余量、再生状态（本版没有再生）。
- 工人稳定 ID、控制者、位置、当前阶段、阶段剩余时间、资源目标与最后目标、移动落点。
- 携货种类、数量、该批货物锁定的单件重量；数量用整数，持久化重量建议用整数克。
- 当前采集批次和锁定耗时、持续/一趟、本轮结束、同类续采、按顺序的后续命令。
- 仓库/以后建筑的稳定 ID、位置和库存；路障/通行状态。

工人的模型、选中圈、LineRenderer、Unity InstanceID、相机和鼠标悬停不进存档。队列中的目标使用稳定 ID，不能序列化 MonoBehaviour 引用。实时寻路路径不存；恢复后重新寻路。

关系表草案在 `backend/database/001_initial.sql`：

| 表 | 用途 |
| --- | --- |
| `game_accounts` | 内部玩家 ID；外部身份提供商的 subject，暂不自建密码库 |
| `game_rule_versions` | 发布后不可随意覆盖的采集规则版本及内容哈希 |
| `game_worlds` | 当前检查点、版本号、tick、规则版本；世界写入租约和 fencing token |
| `world_members` | 谁能进入世界、谁能下令，角色为 owner/controller/viewer |
| `command_receipts` | 命令 ID、请求内容哈希、每单位结果、提交版本；断线重发返回同一个结果 |
| `resource_transfers` | 同一事务产生的经济转移：源头→工人、工人→仓库；以后仓库→建造消耗 |

JSONB 需要服务端 DTO/JSON Schema 校验；数据库的“JSON 对象”检查不等于验证完整世界。稳定字段、所属权、资源非负、载重、任务引用、规则版本兼容、每种资源守恒都由权威模拟与提交验证共同负责。以后需要跨世界交易、独立背包或大规模查询时，再将相应余额/物品拆成关系表，不让两个版本各自成为库存真相。

## 一次入库如何避免重复加货

假设工人 W 携带 6 木材。入库后的检查点必须同时写入“W 携货=0”和“仓库木材+6”，并追加 W→仓库的 6 件转移记录。三者属于同一个数据库事务。

建议提交顺序：

1. 校验内部调用、世界进程租约、fencing token、基础 revision 和规则版本；对 `game_worlds` 行加锁。
2. 查找同一 `(world_id, actor_id, command_id)` 的 receipt。相同命令 ID、相同请求哈希返回原结果；哈希不同拒绝，不能把另一条指令当重试。
3. 用已发布规则校验新的完整状态、经济转移及守恒。按固定 tick 边界将模拟状态冻结成不可变 DTO。
4. `UPDATE game_worlds ... WHERE revision = expected_revision AND writer_epoch = expected_epoch AND lease_until > now()`；恰好更新一行才能继续。
5. 插入这个 revision 的资源转移和本批已执行命令 receipts；一并提交，失败整体回滚。
6. 数据库 commit 成功后，才给玩家发“已持久化”的结果，并推进内存的已提交基线。

并发创建相同 receipt 的唯一键冲突应回滚本次事务，再读已有 receipt；不能在已失败的 PostgreSQL 事务里继续写入。租约续期同样校验 epoch；接管世界时递增 epoch。仅依赖租约过期时间不足以防旧进程恢复后写入。

不要先改仓库、过几秒再单独保存携货。不要在存档重载时再次执行一个已经入库的命令。第一版禁止跨世界经济转移，因此不需要分布式交易。

## 保存频率和失败承诺

先用 1 秒 tick 批次作为持久化实验值，另在退出前保存；它不是上线性能指标。小世界每批提交完整检查点，批内命令、采集和入库事件与检查点同事务。无变化时不写；观察 CPU、存档体积、事务延迟后再调整周期。

客户端区分“收到/正在处理”“模拟结果（尚未持久化）”“已提交 revision”。如果允许画面先展示模拟结果，进程崩溃时最多回退到最后已提交检查点，暂未确认的命令可重发；已持久化确认不能回退。后端无法存档时暂停进一步经济结算，保留未提交批次并重试，不无限推进库存。建造支付、交易和购买以后需要更明确的即时提交边界。

如果玩家要求每次操作都立即可靠确认，可缩短批次或增加命令 WAL/outbox；先测小世界的整份存档，不直接搭事件溯源系统。统计采样可以批量异步写，不能阻塞采集结算。

## 断线、恢复和采集中途存档

- 重新登录先获取检查点 revision，再请求最新运行状态。客户端按 snapshot revision/服务器事件序列去重；网络快照可快于落盘频率，协议必须区分二者。
- 第一版离线默认暂停该玩家的私人世界，不按客户端本机时间补算资源；多人世界有其他在线成员时继续运行。离线收益若要做，另定上限、服务器时钟和结算幂等键。
- 只在完整 tick 边界保存。恢复时：资源已收获则在携货中，已入库则只在仓库，不能重复生成。
- 当前建议恢复策略：正在采集但尚未产出的批次取消预约并将采集进度归零；保留目标并重新申请工作位。已经收获的携货完整保留。等候队列根据持久化的排队票号重建，工作位和卸货位重新分配，受阻路线重新检查。此策略需要在正式接存档前向玩家说明，避免默认承诺无损保留采集中途进度。
- 回滚恢复旧版本需要暂停世界，检查 schema/规则迁移与经济账目；不要拿旧检查点覆盖正在运行的新世界。

## API 草案

- `POST /v1/worlds`：创建私人世界、owner 成员和初始检查点，同一个事务。
- `POST /v1/worlds/{id}/join`：检查身份/成员权限并获得世界连接信息，不直接暴露数据库凭证。
- 世界连接发送 `{commandId, workerIds, type, targetId/point, append, once}`；`actorId` 由服务端从身份注入。队列修改应使用稳定 `orderId`，不能依赖客户端数组下标。
- 返回 `{commandId, revision, acceptedWorkers, rejectedWorkers:[{id,reason}], durability}`。拒绝也保存 receipt，避免同一重试命令在稍后状态改变时突然生效。
- `GET /v1/worlds/{id}/snapshot`：有权限的成员读取服务端允许公开的视图，不能将所有其他玩家私有数据直接返回。
- 内部 checkpoint 提交：只允许被分配的世界进程调用；请求体带 expectedRevision、writerEpoch、state、receipts、transfers，客户端没有此权限。

初期连接协议按实时游戏需求选择并做带宽测试；ASP.NET 的登录/管理 API 和世界实时连接不必采用同一协议。

## 接入顺序和验收

1. 现在：采集统计与场景对照，已加入 Unity；报告文件是调参数据，不是可恢复存档。
2. 下一步：版本化本地 DTO 存档、稳定实体/任务 ID、临时文件写入后替换、保留上一份完整存档。测试携货/采集中途/排队/封路退出再进入。
3. 后端试验：本地 PostgreSQL + ASP.NET，先做单世界提交/读回、版本冲突、同 ID 同请求重试、同 ID 不同请求拒绝、事务中途失败回滚。当前 SQL 是待运行验证的草案，不代表服务已存在。
4. 小规模联机：服务端权威模拟、成员控制权限、断线重连、旧进程 fencing；客户端修改内存库存不影响服务端。
5. 验收：杀进程重启不重复产出；各资源守恒；重复命令只结算一次；不同进程写入冲突可拒绝；数据库不可用时不继续对外确认经济结果；备份可实际还原。

上线前采用独立迁移角色与业务角色，业务角色不能改表；数据库仅在后端私网开放，凭证不放入 Unity 包。部署预算、预期同时在线人数、是否玩家交易和离线收益仍需要在联机阶段确定。
